## Main question: does the skip ever change a result?

I found no case where it does. For each path I listed what the full check reads. Each item is either in the key or checked again on every run.

**ChatGPT** (`quickDone` / `quickKey` / `rememberQuick`):
- Redrawing the note (`refreshView`) depends on the chat, `item.project.name`, the note, view, raw and older paths, the versions, `viewHash`, and the path and presence of each saved file. All of these are in the key: the raw pages through size + mtime, the chat item through `JSON.stringify(item)`. The account label is left out of `viewHash`, so the full check ignores it too. No plugin setting changes how a note is drawn. `editedNotes`, `noteHash` and `synced` only matter when a note is rewritten, and a rewrite only happens when the key differs.
- Downloading files (`backfill`) only does something when a file is missing. Any missing file forces the full check, through `quickDone`'s check and the presence flag in the key. So `assetRetries`, `pendingAssets` and the per-run attempt budget behave as before. The new test proves this (see below).
- Reading saved files (`readSaved` → capture): when it fails, that comes from file content or from paths and page counts. All are covered by the stamps, `older` and `pageHashes`.
- Restore and the missing-guard: a deleted note or raw page gives a null key, so the full check runs. The guard runs before the loop and is unaffected.
- Renames and the move row: `followRename` and the move row change `entry.md`, `entry.json` and `fileIndex` paths, which are all in the key.

**Claude** (step 7): the full check fetches `chatFiles(chat)` and, when the chat view is read, the files found there. Without a view read, that list is the same as `quick.files` for the same raw file, and `missingId` is evaluated live on every run. A view read only happens when `outputsChecked` is behind or `chatFileDeleted` is true, and both are checked live. Restoring notes (step 6) runs before step 7 and marks those chats as done.

**Several computers, merging, Refresh index, mobile:** the key is always computed from this computer's own files. An entry merged in from another computer, or kept by Refresh index, can only be skipped when every fact in its key matches here. Different mtimes on another machine just mean a full check. Mobile has `adapter.stat`. If stat or `manifest.dir` is unavailable, the key is null and the full check always runs.

**Leftover risk:** a raw file rewritten with the same size and the same mtime (to the millisecond) would be skipped. I found no code path that does this.

## For you to decide (no todo tests: these are cost questions, not wrong results)
- **The biggest chats never get the shortcut.** In your real index (`computers/Tower.json`, read-only), ChatGPT has 466 files on `assetRetries`, all at 8–9 attempts (one try a week). They belong to 82 of the 958 saved chats, and those chats hold **172 of the 410 MB** of raw pages. A missing file always forces the full check, so about 42% of today's reading stays. The result would be the same if `quickDone` could also skip a chat whose missing files are all still waiting (`assetRetries[id].nextAttempt > now`). It would then have to add those IDs to `pendingAssets`, as `backfill` does, and `rememberQuick` would have to accept "missing but waiting" as settled. That is a design change, so I did not make it. The same applies to ChatGPT files marked `skipped:` (`missingId` counts them as missing).
- **About 1,000 index writes after every plugin update.** Each change to a chat's remembered key calls `saveSettings`, which writes the whole computer file (`Tower.json`, 2.4 MB, and growing with the keys). A new build changes every key: about 876 ChatGPT and 150 Claude chats, so roughly 2.5 GB of writes in one sync. The same happens on the first run and after every development rebuild of `main.js`. Losing a key on a stop only costs one reread, so one save at the end of the loop (or every N chats) would be enough. This is your call, because the ledger promises "Index saved after every chat".
- **A note that only matches by content is never remembered.** If `refreshView` returns early because the note's text matches but `entry.viewHash` is stale, `rememberQuick` stores nothing, and that chat is fully read on every run. This is only a cost. I don't know how often it happens.

Commits: `7c106a1` (Claude tests), `532694f` (ChatGPT `testQuickCheckSameResult`). The ChatGPT test runs the real `runGptSync` and checks the note text and the result counters, not just how many reads happened.

- ChatGPT: `pageHashes` alone. They only change together with the raw pages' size and mtime.
- ChatGPT: `g.downloadFiles` in the key. When downloads are turned on, `quickDone`'s missing-file check covers it.
- Already caught by the PR's own tests: dropping the stamps, `viewHash`, the note's presence, or the build stamp.
